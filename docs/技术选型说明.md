# 技术选型说明

> 本文回答两个问题：**为什么用这些**，以及**为什么没用推荐清单里的那些**。
> 结论先行：推荐清单里的 shadcn/ui、Radix UI、Magic UI、Aceternity UI、Lucide React、Motion、
> Tailwind CSS、react-resizable-panels、dnd-kit、Zustand、TanStack Query、Recharts 全部是
> **React 生态**，而本项目的前端是 **Vue 3（管理后台）+ uniapp（小程序，Vue 语法、非 DOM 环境）**。
> 直接套用会带来"换框架"级别的返工，因此按每一条的**能力诉求**在同生态里找等效方案，而不是照单引入。

---

## 1. 约束条件（先看这个，选型才有依据）

| 约束 | 实际情况 | 对选型的影响 |
|---|---|---|
| 运行环境 | Windows + **JDK 8** + Maven 3.9 + MySQL 8 | 后端只能落在 Spring Boot **2.7.x**（3.x 需 JDK17），不能上 Spring Boot 3 |
| 小程序 | 微信小程序（渲染层非 DOM，尺寸单位 rpx） | 一切依赖 DOM/`window`/CSS-in-JS 运行时的库不可用；Tailwind 需额外编译链且收益低 |
| 后台 | 桌面 Web | 可用成熟组件库，但主题必须能深度定制到"墨/纸/金/朱砂" |
| 视觉要求 | 古风、简洁现代、统一设计语言 | 必须**令牌驱动**，能全局改色改字号；组件库要支持主题变量覆盖 |
| 依赖要求 | 严格控制、按需安装、不重复引入同类库 | 每引入一个库都要说明"不可替代性"，否则自研几十行 |
| 素材 | 无 AI 绘图模型可用 | 视觉素材改为程序化生成（Pillow + numpy），不引入设计资源依赖 |

## 2. 推荐清单逐条判定

| 推荐项 | 判定 | 理由与替代方案 |
|---|---|---|
| **shadcn/ui** | ❌ 不适用 | React + Tailwind 的"复制源码"方案，Vue 无对等物。**替代：Ant Design Vue 4**——同样是"源码可控 + 主题可覆盖 + 组件齐全"，且是 Vue 生态事实标准，中后台表单/表格能力比 shadcn 更成熟（虚拟滚动、可编辑单元格、树形表格） |
| **Radix UI** | ❌ 不适用 | React 专用无样式基元。**替代：Ant Design Vue 内置无障碍实现**（焦点管理、键盘导航、ARIA），无需再引一层 |
| **Magic UI** | ❌ 不适用 | React + Motion 的动效组件集，且视觉风格（光晕、粒子、渐变边框）与"克制古风"直接冲突。**替代：自研 CSS 过渡**，只保留 opacity/transform 两类属性 |
| **Aceternity UI** | ❌ 不适用 | 同上，且大量使用 SVG 滤镜与滚动监听，小程序不支持 |
| **Lucide React** | 🔁 换生态 | **改用 `lucide-vue-next`**：同一套图标几何语言（24 网格、1.5px 描边、圆角端点），Vue 官方移植，图标可按需 tree-shake。小程序端不引图标库，用 `uni-icons` 字体图标（小程序不支持内联 SVG 的可靠渲染） |
| **Motion（Framer Motion）** | ❌ 不适用 | React 专用，且体积大（~30KB gzip）。本项目动效只有四种：淡入上移、抽屉滑入、hover 变暗、骨架扫光——**用 CSS `transition` + 4 个时长令牌实现，零运行时开销**；小程序端 Motion 完全不可用 |
| **Tailwind CSS** | ❌ 不适用 | ① uniapp 需 `weapp-tailwindcss` 之类额外编译链，rpx 单位支持绕；② 本项目尺寸全部走 **设计令牌 → SCSS 变量 → rpx**，已经解决"统一"，Tailwind 的原子类反而制造第三套真值；③ 后台用 Ant Design Vue 自带样式体系，混入 Tailwind 会有权重冲突。**替代：tokens.scss / tokens.css + 少量手写原子类** |
| **react-resizable-panels** | ❌ 不需要 | 后台是"侧栏 + 内容"的固定结构，唯一需要的是侧栏折叠（216px ↔ 64px），一个 `width` 过渡即可，引入拖拽分栏库纯属过度设计 |
| **dnd-kit** | ❌ 不需要 | 需求是"从图鉴里**挑选**时装组合成搭配"，本质是**多选 + 排序展示**，不是自由拖拽排版。且小程序端触摸拖拽性能与手势冲突严重。**替代：选择式交互（多选弹层 + 已选缩略条，可上下移调整顺序）** |
| **Zustand** | 🔁 换生态 | Vue 对等物是 **Pinia 2**（官方推荐、Vue DevTools 支持、TS 推导完整），同样是轻量 store，不引 Redux 那套 |
| **TanStack Query** | ❌ 不适用 | ① 其 Vue 适配器存在但项目里只有"取列表/取详情"两类请求；② 小程序端 `uni.request` 需要统一封装 token、401 重登、loading 与错误 toast，现成库反而要绕开。**替代：自研 `useRequest` 组合式函数 + `uni.request`/`axios` 封装**（约 80 行，四态齐全：loading/empty/error/success） |
| **Recharts** | ❌ 不适用 | React 组件库。**替代：手写 SVG**——后台只有部位分布、稀有度分布、7 日趋势三个图，用 `<rect>`/`<path>` 画，代码量与引 ECharts（~350KB）相比更小，且能完全贴合令牌配色 |

> **对照推荐的初衷**：清单里那些库的价值是"少造轮子、视觉统一、交互流畅"。本项目用
> Ant Design Vue（组件）+ design tokens（视觉）+ uni-ui（小程序原生能力）达成同一目标，
> 且**依赖数量从 12 个降到 6 个**，符合"严格控制依赖、不重复引入功能相似的库"。

## 3. 最终技术栈与理由

### 3.1 服务端（`backend/`）

| 组件 | 版本 | 为什么是它 |
|---|---|---|
| Spring Boot | 2.7.18 | 本机 JDK 8，只能落在 2.7 线；2.7 是 2.x 最终维护版，生态最全 |
| MyBatis-Plus | 3.5.5 | JeecgBoot 官方采用，`IPage` 分页、逻辑删除、条件构造器正好对应接口契约里的 `pageNo/pageSize/column/order` |
| MySQL | 8.0（本机） | 需求指定；`utf8mb4` 存中文与生僻字（如"鎏""绛"） |
| java-jwt | 3.19.4 | 轻量、无额外传递依赖，实现 JeecgBoot 的 `X-Access-Token` 机制 |
| Lombok | 随 Boot 管理 | 减少实体样板代码 |

**为什么不是直接拉 JeecgBoot 单体？**
JeecgBoot 的完整工程包含代码生成器、在线报表、工作流、消息中心、Redis 会话、Shiro 权限体系等大量模块，
且核心 starter 主要来自其私有/镜像仓库；本项目只有"时装 + 搭配 + 收藏"三张业务表和两类用户角色，
引入完整单体意味着**几十 MB 与本需求无关的依赖**，直接违背"严格控制依赖"。
因此采取：**沿用 JeecgBoot 的工程规范与接口契约**（`/jeecg-boot` 上下文、`Result<T>` 包装、
`{records,total,size,current,pages}` 分页、`X-Access-Token`、`getDictItems/{dictCode}` 字典机制、
Controller/Service/Mapper 分层、MD5+盐口令），后端实现保持轻量。
**收益**：接口形态与 JeecgBoot 完全一致，未来若要迁回官方单体，只需替换 starter 与配置，业务代码与前端零改动。

| Vite | 5.4.11 | 启动快、按需构建 |
| Pinia | 2.3.0 | 官方状态管理 |
| Vue Router | 4.5.0 | 路由 + 页签 |
| axios | 1.7.9 | 拦截器实现 token 注入与 envelope 解包 |
| lucide-vue-next | 0.468.0 | 与推荐清单同一图标语言 |
| TypeScript | 5.6.3 + vue-tsc 2.1.10 | 类型即文档；`vue-tsc --noEmit` 作为构建门槛 |

### 3.3 小程序端（`miniapp/`）

| 组件 | 版本 | 为什么是它 |
|---|---|---|
| uni-app（Vue 3 + Vite） | 3.0.0-5020620260917001 | 需求指定；一套代码出微信小程序 + H5，便于无小程序环境时演示 |
| uni-ui | 1.5.12 | 官方组件库，`uni-popup`/`uni-icons` 等与小程序渲染层兼容性最好，避免自研浮层踩坑 |

### 3.4 为什么用 pnpm workspace 且 `hoist=false`

后台要 Vue 3.5（Ant Design Vue 4 的推荐版本），小程序锁死 Vue 3.4.21（uni-app 的硬约束）。
二者若被提升到同一个 `node_modules/vue`，必然有一端运行时崩。
`.npmrc` 里 `hoist=false` + workspace 分包让两者的 Vue 各自落在自己的 `node_modules`，
这是本项目能在同一仓库里同时满足"后台最新"和"小程序必须旧"的关键。

## 4. 设计令牌：为什么用脚本生成而不是手写两套

后台用 CSS 变量、小程序用 SCSS 变量 + rpx。若各自手写，改一次主色要改两处，**"统一设计语言"就只是口号**。
因此：`design/tokens.json` 是唯一真值，`scripts/gen-tokens.mjs` 一次生成两端产物，
小程序端的长度单位自动 ×2 转 rpx（750 设计稿）。
`scripts/verify.mjs` 会检查生成物是否比 `tokens.json` 旧，防止"改了令牌忘了重新生成"。

---

## 5. 视觉素材：为什么是程序化生成

本机**没有可用的图像生成模型**（调用返回"未配置模型"）。在这种情况下有两条路：
外购/盗用素材（不可接受），或程序化生成。
项目选择后者：`scripts/gen_art.py` 用 Pillow + numpy 按"宣纸底 + 色场 + 墨晕 + 服装剪影 + 金线内框 + 竖排单字"分层绘制，
随机种子取 id 哈希保证可复现。好处是**风格绝对统一、可重新生成、无版权风险**；
代价是写实度不如 AI 出图——这在"图鉴卡片 + 徽记式竖排大字"的展示形态下是可接受的。

        mysql-connector-java, java-jwt, lombok, spring-boot-starter-test
